# 労働時間制と時間外の判定

KIZAMI が扱う労働時間制ごとに、**時間外労働をいつ・何と比べて判定するか**をまとめます。
この判定の違いが、月次一覧に出る列の違いにそのまま表れます。

対象読者は実装者とレビュアーです。労務担当者向けの説明は VitePress のガイド側にあります。

## 制度によって「時間外」の意味が変わる

| | フレックスタイム制 | 固定時間制 |
| --- | --- | --- |
| 判定の単位 | **清算期間(1ヶ月)** | **1日 と 1週** |
| 比べる相手 | 月の総枠 | 1日8時間 / 1週40時間 |
| 日別の法定時間外 | **存在しない** | 存在する |
| 根拠 | 労基法32条の3 | 労基法32条 |

フレックスで1日10時間働いても、清算期間の総枠に収まっていれば時間外ではありません。
**日別の法定時間外が出ないのは実装漏れではなく、法律上そうである**ということです。
このため月次一覧では、フレックスのとき時間外列を出しません。出すと「今日は時間外0だった」
という誤った理解を与えます。

逆に固定時間制では、月末を待たずにその日のうちに時間外が確定します。

## 固定時間制の判定順序

二重計上を防ぐため、**必ず日次 → 週次の順**で計算します。

```
日ごと:
  日次法定時間外 = max(0, 実労働 − 1日の法定労働時間(480分))
  法定内労働     = 実労働 − 日次法定時間外

週ごと(週起算曜日から7日):
  法定内労働を日付昇順に累積し、週の法定労働時間を超えた分を
  その日の週次法定時間外とする
```

先に週で判定すると、1日8時間超として既に時間外にした分を週の集計にも入れてしまい、
同じ労働を二度数えます。

**所定外だが法定内**(いわゆる法定内残業)は割増賃金の対象外ですが賃金は発生するため、
`extraWithinStatutoryMinutes` として法定時間外と区別して保持します。所定7時間の会社で
7時間30分働いた30分がこれにあたります。

法定休日の労働は日次・週次のどちらの計算からも除外し、`legalHolidayMinutes` として
別枠で持ちます(割増率が異なるため。労基法37条1項)。

### 1日8時間は特例措置対象事業場でも変わらない

特例措置対象事業場(商業・映画演劇業・保健衛生業・接客娯楽業のうち常時10人未満)で
緩和されるのは**週の法定労働時間だけ**(40時間 → 44時間)で、1日8時間は動きません。
労基法40条・労基則25条の2。

このため `LawRules` は `dailyStatutoryMinutes` と `weeklyStatutoryMinutes` を別に持ち、
テナント属性 `isSpecialProvisionWorkplace` は後者にだけ効きます。

### 週の起算曜日

週40時間の判定には週の区切りが要ります。就業規則に定めがなければ日曜起算が原則
(昭和63年基発第1号)なので、`tenant_setting_versions.week_start_weekday` の既定は 0(日曜)です。

**月をまたぐ週は、その月の期間内にある日だけで判定します。** 前月分を引きずりません。
月次集計の独立性(締めた月が後から動かない)を優先した割り切りで、月初の週で週次法定時間外が
実際より少なく出ることがあります。清算を厳密にする場合は週次の締めが必要になるため、
将来の課題として残しています。

## 有給の扱いが制度で違う

| | フレックス | 固定時間制 |
| --- | --- | --- |
| 有給取得日 | **総枠に算入**(actualMinutes に足す) | **時間外判定に関与しない** |

フレックスでは「働いたことにして総枠と比べる」必要があります。有給を取った日を0分として
扱うと、その月だけ総枠不足になり不当な控除につながるためです。

固定時間制では、有給は所定労働日の欠勤を打ち消すだけで、1日8時間・週40時間という
実労働に対する上限とは無関係です。有給を足して週40時間を超えたことにするのは誤りです。

## 期間の途中で制度が変わったら

`settingsTimeline` の span ごとに労働時間制が変わりえます(契約変更など)。
エンジンは**期間開始日に有効だった制度**で月全体を計算し、期間内に別の制度が混在していれば
`mixed_work_system` 警告を出します。

これは「閾値は期間開始日基準」という既存の流儀(`flex.ts` の判断点コメント参照)と揃えたものです。
月の途中で制度が切り替わる運用を正しく集計するには、清算期間を分割して2本の集計を
合成する必要があり、現時点では警告で気づかせるにとどめています。

## コアタイム(フレックスのみ)

**根拠**: 労基法32条の3。コアタイム(必ず勤務すべき時間帯)を定めるかどうかは労使協定の
**任意事項**で、定めなければいわゆるスーパーフレックスになります。KIZAMI の既定は
「コアタイムなし」です。

### 措置の性質は「警告だけ」

コアタイム中の不在は制度上「遅刻・早退」として扱えます。しかし**集計は一切変わりません**。
フレックスの時間外は清算期間の総枠との差でしか決まらないため(上表)、コアタイムを外れても
実労働は1分も増減しないからです。賃金を控除するかどうかは給与側の判断であり、
KIZAMI は事実を計測して警告するところまでを担います
(休憩の自動控除と同じ立場 — [breaks.md](./breaks.md)「自動控除は便利機能ではなく危険な機能」)。

実装上も `totals` / `flexBalance` には触れず、`EngineOutput.warnings` に3種の警告を足すだけです。

| 警告 | 条件 | `core.deltaMinutes` |
| --- | --- | --- |
| `core_time_late_arrival` | 最初の出勤がコアタイム開始より遅い | 開始から出勤までの分(帯の長さで頭打ち) |
| `core_time_early_leave` | 最後の退勤がコアタイム終了より早い | 退勤から終了までの分(同上) |
| `core_time_absence` | 対象日に実労働が0分 | コアタイムの帯の長さ |

判定は `packages/engine/src/core-time.ts`。シフトの予実突合(`shift-variance.ts`)と同じく
**最初の出勤・最後の退勤だけ**を見ます。コアタイム中の中抜けは検知しません — 中抜けの是非は
休憩ルールの領分で、コアタイムとしては「帯の端に居たか」が分かれば足りるという整理です。

### コアタイムはいつ適用されるのか

不在(`core_time_absence`)を正しく出すには「その日が働くべき日か」を知る必要があります。
フレックスにはシフト制の `ShiftDay` のような**所定労働日カレンダーが無く**、エンジンが
日付から判定できる休みは法定休日だけです。土曜のような所定休日(法定休日ではない非勤務日)を
区別できないまま不在を出すと、週休2日の会社では毎週土曜に誤報が出ます。

そこで**コアタイム設定自体に適用曜日を持たせます**(`CoreTime.weekdays`、既定は月〜金)。
実務でもコアタイムは「平日10:00〜15:00」のように曜日とセットで定められるため、
所定労働日カレンダーという新しい機構を導入せずに済みます。

適用対象から外す日:

- 法定休日 — その日に働くこと自体が例外で、遅刻・早退を重ねて言う意味がない
- `weekdays` に含まれない曜日 — 上記のとおり所定休日を表す
- 有給を取得した日 — 全休はもちろん、時間単位年休でコアタイムの一部を休んだ場合も
  「承認済みの不在」であって遅刻・早退ではない。有給は分数しか持たず取得した時間帯が
  分からないため、重なりを厳密に見ることはできず、日単位で丸ごと除外する保守的な扱いにしている
- `EngineInput.asOfDate` 以降(当日を含む) — まだ来ていない日・進行中の当日を
  「不在」と断ずるのは誤報(`shift_absence` と同じ扱い)

### 帯の表現

`startMinutes` / `endMinutes` はローカル0時からの分で、**日跨ぎは表現しません**
(`startMinutes < endMinutes` を必須とし、`POST /settings/work-policy` が 400 で弾きます)。
コアタイムは「1日の中の、全員が居るべき日中の帯」という制度前提であり、夜勤の帯を表す必要が
ないためです。日跨ぎを許すと「その帯はどの勤怠日に属するのか」を、シフト制と違って所定の
裏付けが無いまま解く必要が出てきます。

永続化は `work_policy_versions.core`(text)に JSON で入れます
(`{"startMinutes":600,"endMinutes":900,"weekdays":[1,2,3,4,5]}`)。
法定休日ルール・休憩ルールと同じ「構造を持つ設定値は JSON 1列」の流儀で、他の設定と同じく
**effective-dated** です — コアタイムを後から追加しても、過去の月の警告は変わりません。

## 名前付きの制度と時短勤務(2026-10-05、第1段階: 固定時間制)

育児・介護の短時間勤務(育児・介護休業法23条)では、同じ会社の中で「一般は所定8時間、
時短の人だけ所定6時間」が普通に起きます。以前は制度の種類(flex / fixed / monthly_variable)ごとに
テナント1本の制度を共有し、メンバーへの割当を「種類を選ぶ」ことで表していたため、これを
表現できませんでした。

### 制度は名前を持ち、メンバーには制度を割り当てる

テナントは制度(`work_policies`)を**名前付きで複数**持てます(例:「固定(8時間)」
「固定・時短(6時間)」)。所定労働時間は制度の版(`work_policy_versions.standard_day_minutes`)が
持ち、メンバーには制度の id を割り当てます(`user_policy_assignments.work_policy_id`)。
制度・割当・版はどれも effective-dated で、版を足しても過去の集計は変わりません。

DB とエンジンはもともとこの形を扱える作りでした。足りなかったのは API と画面です。

| 操作 | API | 監査ログ |
| --- | --- | --- |
| 制度の一覧(現在の版・版の履歴・割当人数) | `GET /settings/work-policies` | — |
| 制度の作成(名前・種類・初版) | `POST /settings/work-policies` | `work_policy.create` |
| 名前の変更・アーカイブ | `PATCH /settings/work-policies/:id` | `work_policy.rename` / `work_policy.archive` / `work_policy.unarchive` |
| 版の追加 | `POST /settings/work-policies/:id/versions` | `work_policy_version.create` |
| メンバーへの割当 | `POST /members/:id/work-policy`(`workPolicyId`) | `member.work_policy.assign` |
| 招待と同時の割当 | `POST /members`(`workPolicyId`、任意) | `member.invite` |

権限はすべて、勤怠ルールの労働時間制と同じ `tenant_settings.flex.manage`(テナント全体)です。
所定は賃金に直結するため、メンバー管理系(`member.*`)の権限では割当を変えられません。

- **固定時間制の所定は 1〜480 分**。1日8時間を超える所定は、通常の固定時間制では法定労働時間を
  超える所定を定めることになり成り立たない(変形労働時間制の協定が要る)ため、全経路で受け付けない
- **名前の重複は不可**(テナント内、アーカイブ済みも含む)。DB の一意制約にはせずアプリ層で検査する
  — 既存のテナントに同名の行があってもマイグレーションを失敗させないため
- **割当の入口で版の有無を検査する**。割当の適用開始日の時点で有効な版が無い制度
  (初版が将来日)を割り当てると、その間の月次・有給で版が解決できず 500 になるため、
  `409 work_policy_not_effective_yet` で止める。アーカイブ済みは `409 work_policy_archived`
- 従来の「種類を指定する」割当(`{ kind }`)は後方互換のために残し、**その種類の既定の制度**
  (アーカイブ済みを除いた作成順で、最新版の種類が一致する最初の制度)に割り当てる

### 既定の制度

テナントで**最も古い制度**(作成時刻 → id の順で先頭)を既定の制度とします。専用の列は持ちません
— 既存のテナントで「どれが既定か」が、マイグレーションなしで今までと同じに決まるためです。

- 招待で作られたメンバーには、入社日(未入力なら今日)から既定の制度を自動で割り当てる
  (割当が無いと有給・月次が 500 になる)。招待の時点で別の制度を選ぶこともできる
  — 招待と同じ日から別の制度にしたいとき、後から割当を足すと同じ日の重複
  (`409 assignment_already_exists`)になって直せないため
- 従来の `GET/POST /settings/work-policy`(テナントに1本の制度の版管理)は既定の制度を対象に
  動き続ける
- 既定の制度はアーカイブできない(`409 cannot_archive_default_work_policy`)。既定を別の制度へ
  切り替える操作は第1段階では用意していない

### 削除はせず、アーカイブにとどめる

制度は版と割当の履歴から参照されているため、削除すると過去の月次が再計算できなくなります。
代わりに `work_policies.archived_at` を足し、アーカイブした制度を**新しい割当の選択肢から外す**
だけにしました。既に割り当てられているメンバーの計算は変わりません。版の追加はアーカイブ後も
できます(割り当て済みの人の所定を直す必要は残りうるため)。

### 「ユーザーの労働時間制」を割当から解決していることの確認

時短の人の計算が黙って一般の人の所定で行われないよう、ユーザーの制度を解決する箇所を確認しました。
集計に使う経路はすべて `buildSettingsTimeline`(`apps/api/src/lib/settings.ts`)を通り、
**割当(`user_policy_assignments`)→ その制度の版**の順に解決しています。kind で制度を探す経路は
集計にはありません。

| 経路 | 解決のしかた |
| --- | --- |
| 月次(`GET /attendance/monthly`) | `buildSettingsTimelineWithBaseDayMinutes` |
| 有給(残高・申請・承認・失効アラート・付与の予告) | `routes/leave.ts` の `loadBalanceContext` → 同上、`leave-grant-proposals.ts` → `buildSettingsTimeline` |
| 締め・締め後修正 | `lib/closing-amend.ts`(テナント単位の版を共有しつつ、割当は人ごとに引く) |
| CSV・給与ソフト向けエクスポート | 締め済みはスナップショット、未締めは `calculateMonthlyForUser`(`reminders.ts`、中身は `lib/closing-amend.ts` の `computeMonthlyForUser`)→ 同上 |
| 打刻忘れ・36協定・シフト乖離のアラート | `calculateMonthlyForUser` → 同上(シフト制の変形期間は `lib/monthly-shifts.ts` も同じ関数で解決) |
| MCP | API(`/leave/balance`・`/attendance/monthly`)の結果を使うだけで、自前で解決しない |

kind で制度を選んでいたのは、割当の入口(`POST /members/:id/work-policy` の `{ kind }`)と
メンバー一覧のバッジだけでした。前者は後方互換の入力として残し、後者は制度の id と名前も
返すようにしました。混在する月の結合テストは `apps/api/test/short-hours-work-policy.test.ts`。

### 次の段階: フレックスの契約上の枠

フレックスでも名前付きの制度は作れますが、第1段階で人ごとに効くのは**標準労働時間**
(有給1日の換算)だけです。清算期間の総枠は、今のエンジン(`packages/engine/src/flex.ts`)では
**法定の枠**(週の法定労働時間 × 暦日数 ÷ 7)の1本しかありません。

- `flexBalance.frameMinutes` は法定の枠で、`diffMinutes`(過不足)もこれと比べる。
  所定6時間の人は毎月大きな「不足」と表示されてしまう
- 法定の枠を超えた分が法定外(`overtime`)、それ以下はすべて `statutory` に入る。契約上の枠
  (所定総労働時間)を超えて法定の枠以内の部分 — 固定時間制の「法定内残業」に当たるもの —
  を区別する区分がフレックスには無い

時短フレックスに対応するには、契約上の枠を入力として足し、(1) 過不足は契約上の枠と比べ、
(2) 契約上の枠〜法定の枠を法定内残業、(3) 法定の枠超を法定外とする、の3段にする必要があります。
契約上の枠を「所定労働日数 × 標準労働時間」で決めるなら所定休日のカレンダーが要り、
締めのスナップショットとエクスポートの列(`flex_frame_minutes` の意味)にも影響します。
このため別の段階として扱います(docs/design/saas.md「公開前に塞ぐべき既知のギャップ」の3)。

## 未実装の制度

- **変形労働時間制**(1ヶ月単位・1年単位。労基法32条の2 / 32条の4) — 週の法定労働時間を
  期間平均で判定する。所定労働時間をあらかじめ日ごとに特定する必要があるため、
  シフト表の入力が前提になる
- **事業場外みなし労働時間制**(労基法38条の2)
- **裁量労働制**(専門業務型・企画業務型。労基法38条の3 / 38条の4)

いずれも `WorkSystem` の判別可能ユニオンに派生を足す形で入ります。
`EngineOutput.workSystem` を見て表示を変える作りにしてあるため、UI 側の分岐も同じ場所で済みます。
