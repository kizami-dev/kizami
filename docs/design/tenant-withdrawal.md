## 1. 流れ — 申請 → 30日の猶予 → 物理削除

1. **申請**: `tenant.withdraw` を持つ管理者が、設定の「テナントの退会」から申請する。確認ダイアログは影響を
   列挙したうえで**会社名の再入力**を求める(`member.erase` と同じ作法。サーバーも同じ照合をし、一致しなければ
   400 `confirmation_mismatch`)。申請した時点でテナントは「退会手続き中」になり、削除予定の時刻
   (申請 + 30日)が決まる。監査ログ `tenant.withdrawal.request`
2. **猶予期間(30日)**: できるのは**全データのエクスポートと申請の取り消し**だけ(下記 §2)。取り消すと
   すべて元どおりに使える(監査ログ `tenant.withdrawal.cancel`)。削除予定の7日前に再通知のメールを送る
3. **物理削除**: 削除予定の時刻を過ぎたら、worker の定期ジョブ(既定15分ごと)が削除する。運用者 CLI の
   `operator tenant purge <tenant-id>`(テナント id の再入力で確認)からも、予定を待たずに実行できる

`tenant.withdraw` は危険権限・テナント全体のみで、同梱プリセットでは管理者だけが持つ
([permission-catalog.md](./permission-catalog.md) §1.16)。既存のテナントへは
`operator tenant sync-presets` で届ける。

## 2. 退会手続き中の制限

| 対象 | 扱い | 根拠 |
| --- | --- | --- |
| ログイン(パスワード・2FA の第2段階・SSO・パスワード再設定) | `tenant.withdraw` を持つ人だけ。他は 403 `tenant_withdrawing`(SSO は `/login?error=tenant_withdrawing`) | 猶予期間の目的はエクスポートと取り消しだけ。パスワードの判定の**後**で断るので、理由を返しても列挙の材料にならない |
| 招待の受諾 | 全員 403 | アカウントを有効にする書き込み。消えるテナントに新しく参加させない |
| 既存のセッション(`tenant.withdraw` なし) | **消さず**、すべてのリクエストを 401 `tenant_withdrawing`(Web はログイン画面へ戻して理由を出す) | 取り消せば元どおりに使えるのが「取り消し」の意味。消すと全員がログインし直しになる。手続き中のセッションでは何もできないので残す危険もない。テナントの削除で行ごと消える |
| 既存のセッション(`tenant.withdraw` あり) | 閲覧(GET/HEAD)は通す。書き込みは取り消しだけ通し、他は 409 `tenant_withdrawing` | 閲覧はエクスポートの前に中身を確かめるため。既存の CSV エクスポートも GET なのでそのまま使える |

| Slack からの打刻 | 断る(エフェメラルで理由を返す) | 同上 |
| 定期ジョブ(打刻忘れ・36協定・有給・シフトの乖離・有給の予告) | 対象から外す(`listActiveUsers` と有給の予告の一覧で JOIN して除く) | ログインできない人へ通知しても何もできない |

## 3. 物理削除

### 何を消すか

- tenant_id を持つ**全テーブル**の `tenant_id = 対象` の行(`TENANT_PURGE_ORDER`、43表。外部キーを持たない利用上限のカウンタ `tenant_usage_counters` も含め、削除の記録に行数を残す)
- システム表 `pending_signups` のうち、そのテナントを作った確認済みの申込み(下記)
- 最後に `tenants` の行そのもの

**システム表の参照は「行を消す」**(判断点): `pending_signups.tenant_id` を null にするだけだと、
確認済みの行が持つ申込者のメール・氏名・組織名が運用者側に残り続ける。行が消えても困るものは無い
(招待コードの使用回数は `signup_invite_codes.used_count` に残る)。`signup_invite_codes` /
`password_reset_requests` / `worker_heartbeats` はテナントを参照しないので触らない
(`password_reset_requests` はメールのキーを持つが、テナントと結びつかず、定期ジョブが1日で消す)。

削除の後、同じメールアドレスで新しく登録できる(未消費の申込みはメールごとに1行という部分 UNIQUE は、
消費済みの行と関係しない。テスト: `apps/api/test/tenant-withdrawal.test.ts`)。

### 順序とトランザクション

外部キーの**子から親**の順に、テーブルごとに「数える → 消す」の2文を流す。テーブル内の自己参照
(`punch_events.supersedes_id` など)は同じテナントの行を1文で全部消すので問題にならない(SQLite・
PostgreSQL とも NO ACTION の外部キーは文の終わりに検査する)。逆に**別のテナントの行が対象テナントの行を
参照していれば**外部キー違反で止まる — テナント分離が破れたデータを黙って消し進めない安全装置として残す。

- **SQLite・PostgreSQL**: 削除の全体を1トランザクションで行う。途中で失敗すれば何も消えていない
- **D1**(`BEGIN` を使えない): `transactional: false` で、テーブルごとに1文ずつ子から親の順に消す。途中で
  止まっても外部キー違反の状態にはならず(残るのは親の側)、各文は「一致する行をすべて消す」なので冪等。
  テナント行は最後に消すので、止まったテナントは手続き中のまま残り、再実行が続きから完了させる。
  削除の記録はテーブルごとに行数を足し合わせて更新する。`batch()` にまとめる案は採らない —
  node-postgres に無く実装が2系統になるうえ、削除は Workers のエントリからは走らない(定期ジョブも CLI も Node)

### 確認と削除のすき間(2026-10-05 セキュリティレビュー)

「申請中で予定を過ぎている」と確かめてから消すまでの間に管理者が取り消すと、取り消したテナントが
消えうる。そこで**迷ったら消さない側**に倒す:

1. 削除は `tenants.withdrawal_purge_started_at`(「削除中」の印)を**条件付き UPDATE で取れたときだけ**進む。
   WHERE には「申請中・印が無い・(定期ジョブなら)予定を過ぎている」をすべて含める。取れなければ何もしない
2. 取り消しも「印が無い」を WHERE に含める。削除が始まったテナントの取り消しは 409 `purge_in_progress`
3. 印は削除のトランザクションの**外**で確定させる。削除が途中で失敗しても印は残り(取り消しは効かない)、
   次の実行が印のあるテナントの削除を続ける
4. テーブルを1つ消す前に毎回、印が自分の取った値のままであることを確かめる(違えば止める)

取り消しと削除は同じ行への条件付き UPDATE どうしなので、SQLite(書き込みの直列化)でも PostgreSQL
(行ロックで直列化され、後の側は WHERE を評価し直す)でも、どちらか一方だけが成功する。

### テーブルの漏れを防ぐ仕組み

`packages/db/test/tenant-purge.test.ts` が**スキーマから**次を列挙して検査する。テーブルを足して
削除の一覧に載せ忘れると、テストが落ちる:

- tenant_id を持つテーブルがすべて `TENANT_PURGE_ORDER` か `TENANT_PURGE_SYSTEM_TABLES` に載っている
- 削除されるテーブル(と tenants)を外部キーで参照するテーブルが、すべて削除の対象になっている
- `TENANT_PURGE_ORDER` が外部キーの子 → 親の順になっている
- テスト用の fixture(`test/support/full-tenant.ts`)が削除の対象の全テーブルに行を入れている
- エクスポートの扱い(`TENANT_EXPORT_POLICY`)が全テーブル分あり、秘密らしい名前の列はすべて出さない側にある

削除の前後で、**別テナントとシステム表の全テーブルの行数とチェックサム**が変わらないこと、対象テナントの行が
どのテーブルにも残らないことを、SQLite・PostgreSQL・D1 の3つで確かめている。

### 削除の記録(`tenant_purge_records`、システム表)

テナントの監査ログも消えるので、運用者向けの記録をテナントの外に残す。中身は**テナント id・申請日時・
削除の開始と完了の日時・テーブルごとの削除行数だけ**。テナント名・メール・氏名・申請者の id は持たない
(「消した」と言いながら運用者側に会社名が残らないように)。`operator tenant purges` で一覧できる。
tenants への外部キーは張らない(参照先が消えた後に残るための行なので)。

## 4. 全データのエクスポート

`GET /tenant/export`(`tenant.withdraw`)。**退会と関係なく通常の状態でも使える**(データのポータビリティ)。
監査ログ `tenant.export` は**流し始める前に**1件残す(中身も数も残さない。下記「流しながら返す」)。1つの zip:

| ファイル | 中身 |
| --- | --- |
| `README.txt` | 中身の説明と法定保存の案内(日本語・英語)。zip の先頭 |
| `manifest.json` | 形式の版(`kizami-tenant-export` v1)・出力時刻・テーブルごとの行数・除いた列とテーブル。行数を数え終えてから書くので zip の末尾 |
| `data/<テーブル名>.json` | tenants と全テーブルの行(DB の列名のまま、時刻は UTC エポック分) |
| `attendance/monthly/<YYYY-MM>.csv` | 月ごとの集計。既存の汎用CSV(`GET /exports/attendance.csv`)と同じ列・同じ値 |
| `attendance/daily/<YYYY-MM>/<氏名>_<id>.csv` | 月ごと・メンバーごとの出勤簿相当(日ごとの始業・終業〔日本時間〕・労働・休憩・深夜・法定休日・有給) |

**含めないもの**(SELECT の段階で除く): パスワードのハッシュ(`auth_credentials` ごと)、セッション
(`sessions` ごと、id がトークンのハッシュ)、2FA のリカバリコード(`user_totp_recovery_codes` ごと)・
共有鍵とカウンタ、API キー・招待・パスワード再設定・Slack 連携のトークンのハッシュ、プッシュ通知の endpoint と鍵、
暗号化して保存している秘密情報(会社・個人の Webhook の URL、SMTP のパスワード、SSO の client secret、
Slack の signing secret)。利用上限の日ごとのカウンタ(`tenant_usage_counters`)も出さない(運用上の値で、業務データではない)。

CSV は数式インジェクション対策(`lib/csv.ts`、先頭の `= + - @` タブ・CR に `'` を付ける。数値は変えない)を
通す。既存の勤怠の CSV も同じ関数を通る。

出勤簿相当の CSV は、メンバーの打刻・休暇がある最初の月から最後の月まで(今月まで)を途切れなく出す。
zip は fflate(MIT・依存なし・純粋な JS、Node と Workers の両方で動く)。

### 流しながら返す(2026-10-06)

当初は全テーブルの全行を読み、全ファイルを作ってから `zipSync` で1回の応答にしていた。50人 × 3年
(約17万行)で RSS が数百 MB、200人 × 3年で 1.3〜1.8 GB 増え、ホスト版の API コンテナ(上限 512Mi)が
最大規模のテナントの1回のエクスポートで OOM になり、全テナントが巻き込まれる。時間は問題ではなかった。
そこで zip を**引っぱり型のストリーム**で返すようにした(`apps/api/src/lib/tenant-export-archive.ts`):

- zip の中身は async generator で1ファイルずつ・1断片ずつ作り、fflate の `Zip`(同期の Deflate。
  Worker スレッドに頼る非同期版は Node と Workers で同じに動かないので使わない)に流す。`ReadableStream` の
  `pull()` ごとに1つ進めるので、相手が読む速さ以上には作らない(背圧)。Content-Length は付けない
- `data/<テーブル>.json` は `@kizami/db` の `iterateTenantExportTable` が主キーの keyset ページング
  (既定 1,000 行)で読み、ページごとに書き出す。書式は従来の `JSON.stringify(rows, null, 2)` と1バイトも
  違わない。ページングが各ページで索引の範囲読みになるよう、行の多いテーブル(`punch_events`・
  `closing_snapshots`・`closing_events`・`correction_requests`・`leave_requests`・`notifications`・
  `shift_days`)に `(tenant_id, id)` の索引を足した
- 出勤簿相当は1か月・1人ずつ計算してすぐに流す。月ごとの文脈(法令・手当・設定のタイムラインと制度の版)は
  テナント単位の小さなもので、打刻の量には比例しない。「記録がある月」の範囲は打刻を全件読まずに
  `GROUP BY user_id` の MIN/MAX で求める
- 中身は従来と同じ(同じファイル・同じ JSON・同じ CSV の列と値・同じ除外・同じ README。形式の版は 1 のまま)。
  50人 × 3年の SQLite・PostgreSQL の両方で、従来の実装と全ファイルの中身が一致することを確かめた

**同時に走る本数と期限**(判断点。`TENANT_EXPORT_*` の定数):

- **テナントごとに1本、プロセス全体で2本まで**。超えたら 429 `export_busy`(`Retry-After: 30`)で、画面は
  「別のエクスポートを作成中」と案内する。プロセス全体の上限はメモリを守るため。2本にしたのは、1本あたりの増分が
  PostgreSQL(ホスト版)で規模によらず +10〜20 MB、SQLite でも2本同時で +60 MB 以下に収まり、かつ1つのテナントが
  枠を握っても別のテナントには必ず1本残るようにするため。テナントごとの1本は、同じテナントが何本も並べて枠を埋めるのを防ぐ
- **流し始めてから10分**で打ち切る(全体の期限)。背圧があるので、ゆっくり読み続ける相手は「読まれない時間」の
  上限だけでは止められない。200人 × 3年が PostgreSQL で約 23 秒・zip 約 25 MB なので、1 Mbps の回線でも収まる
- **次を読みに来ない時間が60秒**を超えたら打ち切る。接続を開いたまま読まない相手や、切れたのに `cancel` が届かない
  場合もこれで枠が返る
- 打ち切りでは generator を閉じ、ストリームをエラーにし、テナント id を console.warn に残し、枠はすぐに返す。
  最後まで流れた・途中で失敗した・相手が切った(`cancel`)ときも返す。ストリームを作る前の失敗(テナントの読み出しや
  監査ログの例外、404)はルートの finally で返す

**知っておくべき割り切り**: プロセス全体の枠は全テナントで共有なので、悪意のあるテナントは期限いっぱい(10分)まで
枠を1つ握れる(テナントごとに1本なので2つは握れず、別のテナントには常にもう1本残る)。エクスポートはまれにしか使わないので、
待たせても実害は小さい。

**イベントループを止めない**: 1回の pull で進めるのは zip のバイト列が出るまで(多くは1人の1か月・1,000 行の1ページ)。
@libsql/client のファイルの SQLite は問い合わせがマイクロタスクのうちに解決するので、そのままだとエクスポートの間ほかの
リクエストが止まる(戻る前は数秒間タイマーが1度も動かなかった)。pull ごとと、20 ミリ秒動き続けたところでイベントループへ
戻る(10ms のタイマーの最大の遅れは 50人 × 3年の SQLite で約 40ms、200人 × 3年で約 220ms。後者は未締めの月の
月ごとの集計 — 全員分の再計算 — が1歩の中で割れないため。従来の CSV のエクスポートと同じ長さ)。zip の断片はファイル
ごとに取り出してすぐに渡し、ファイルをまたいで溜めない(fflate が中央ディレクトリのために持つのはファイルごとの名前・
大きさ・CRC だけ)。

**途中で失敗したとき**: ヘッダー(200)は送った後なので、ストリームをエラーにして接続を切り(ダウンロードの失敗に
見える。末尾の中央ディレクトリが無いので、壊れた zip を正しいものと取り違えることもない)、サーバーのログに残す。

**監査ログは流し始める前に残す**: zip はファイルごとにローカルヘッダーを持つので、途中で切れた zip からも、
切れる前に届いたファイルは取り出せる。完了時に記録する形だと、最後の手前で自分から切れば「ほぼ全員分を
持ち出したのに記録が無い」ことになるため、試みを記録する(失敗・中断した回も1件残り、429 の回は残らない)。
行数などの数は流し終えるまで分からないので監査ログには入れない(zip の `manifest.json` と、完了時の
サーバーのログに出る)。

計測(Apple M4・Node 26。最大 RSS から、エクスポートしない同じスクリプトの値を引いた増分):

| 規模 | 従来(zipSync) | ストリーミング |
| --- | --- | --- |
| PostgreSQL 50人 × 3年(約17万行・1,878 ファイル) | +270〜285 MB・6 秒 | +10〜20 MB・6 秒 |
| PostgreSQL 200人 × 3年(約67万行・7,278 ファイル) | +1.35 GB・18 秒 | +13 MB・23 秒 |
| SQLite 50人 × 3年 | +380〜420 MB・4.5 秒 | +16〜42 MB・4 秒(2本同時 +44〜60 MB・7.5 秒) |
| SQLite 200人 × 3年 | +1.27 GB・18 秒 | +53 MB・17 秒(2本同時 +51 MB・30 秒) |

JS のヒープの増分は規模によらず数十 MB で頭打ちになる。SQLite はイベントループへ戻るようにする前は 200人 × 3年で
+285 MB まで増えていた(@libsql/client のネイティブ側の文のメモリが V8 の GC まで解放されず、戻らないと GC の機会も
無かった)。Cloudflare の 100 秒の制限は最初の1バイトまでの時間なので、流し始めれば規模による時間の上限も実質なくなる。

## 5. 通知(システムメールがある配備だけ)

`SYSTEM_SMTP_URL` / `SYSTEM_MAIL_FROM` / `APP_BASE_URL` が揃っている配備では、`tenant.withdraw` を持つ
**全員**へ(申請した本人だけでなく — 1人の管理者や乗っ取られたアカウントが黙って会社のデータを消せないように)
次のメールを送る。api は申請時、worker は再通知と完了を送るので、**worker にも同じ3つの環境変数が要る**。

| 時期 | 内容 |
| --- | --- |
| 申請時 | 削除予定の日時、保存義務の案内、エクスポートと取り消しの画面へのリンク |
| 削除の7日前 | 再通知(条件付き UPDATE の印で1回だけ) |
| 削除の後 | 完了の連絡(宛先は削除の前に集めておく。記録には残さない) |

文面に**ユーザー入力(テナント名など)を入れない**(signup・本人用のパスワード再設定と同じフィッシング対策)。
リンクは固定のパスだけ。システムメールの無い配備(セルフホスト)では画面の表示(設定画面と全画面のお知らせ)だけ。

## 6. 法定保存の案内

労働基準法109条は出勤簿などの記録を5年間(令和2年改正の附則143条2項により**当分の間3年間**)保存することを
**事業主に**義務づけている([data-retention.md](./data-retention.md) §1 と同じ整理)。KIZAMI がテナントを
削除しても、会社の保存義務は消えない。そのため設定画面(エクスポートを申請より上に置く)・確認ダイアログ・
メール・エクスポートの README のすべてで、削除の前に全データをエクスポートして保存するよう案内する。

## 7. バックアップ

R2 のバックアップ(日次30日・月次400日)には、削除済みのテナントのデータが**期限まで残る**
(dump はデータベース全体の単位で、テナントごとに消せない)。

- バックアップは障害からの復旧にだけ使い、閲覧・分析には使わない
- **バックアップから復元したときは、復元した時点より後に削除したテナントを再び削除する**。手順は
  `deploy/k8s-cloud/README.md` の「復旧手順」(削除の記録 `tenant_purge_records` は削除と同じ dump に入るので、
  復元前の記録を残しておく必要がある)
- プライバシーポリシー(運用者 → テナント)に書くべき事項: 退会後30日で物理削除すること、バックアップには
  最長で約13か月(月次の400日)残り、期限が来れば消えること、バックアップは復旧の目的でだけ使うこと、
  復旧したときは削除済みのテナントを削除し直すこと、削除の記録として個人情報を含まない最小限(テナント id・
  日時・行数)を残すこと
