# @kizami/help-content

画面のヘルプ・通知・ドキュメントで使う説明文の単一ソース(要件 §10)。

1エントリ=1ファイル、`content/<key>.<lang>.md`。同じ内容をアプリのツールチップと
VitePress のドキュメントの両方に供給する。

## frontmatter

```yaml
---
key: leave.mandatory-five-days      # 参照キー(ドット区切り)
audience: [employee, admin]         # 誰に見せるか
origin: law                         # 出所ラベル(下記)
basis: 労働基準法39条7項              # origin: law のとき必須。根拠条文
summary: 一文〜二文。ツールチップに出る短い説明
companyExample: |                   # 任意。社内規定の記入例(プレースホルダに使う)
  申請は取得日の前日までにお願いします。
---
```

### origin — 出所ラベル(必須)

説明の出どころを必ず区別する。混ぜると、法定要件を社内ルールだと誤認して緩めたり、
社内ルールを法定だと思い込んだりする。コンプライアンス製品として最も危険な失敗。

| 値 | 意味 | 変更可否 | 表示 |
| --- | --- | --- | --- |
| `law` | 労基法等が定める要件 | 変更不可 | 「法令」バッジ + 根拠条文 |
| `product` | KIZAMI の仕様・設計判断 | バージョンで変わる | 「KIZAMIの仕様」バッジ |
| `company` | 導入企業が定めるルール | テナントが編集 | 「自社の規定」バッジ |

`content/` に置くのは `law` と `product` のみ。`company` は DB(`help_overrides`)に
テナントごとに保存され、同じキーの下に追記表示される。

### audience — 対象読者

- `employee`: 従業員本人が自分の権利・手続きを知るための説明
- `admin`: 労務担当者が制度を設定・運用するための説明

両方に必要なら両方書く。同じ制度でも「あなたは○日取れます」(employee)と
「付与方式を選びます」(admin)では書くことが違うので、キーを分けてよい。

## 書き方

- **法令の説明(`origin: law`)には必ず `basis` を書く**。根拠のない「法律で決まっています」は書かない
- **判断を誤りやすい点を明示する**。例: 年5日義務に半休は算入できるが時間単位は算入できない
- 「〜してください」ではなく「〜できます / 〜が必要です」。指示ではなく情報として書く
- KIZAMI の仕様(`origin: product`)と法令(`law`)を1つのファイルに混ぜない。分けてキーを2つにする

## companyExample — 社内規定の記入例

導入企業が自社ルールを書くときのプレースホルダ。**何を書かないか**を示すことが最も重要:

- **法令の内容は書き写さない** — 法令部分は自動表示される。重複すると法改正時に
  KIZAMI 側だけ更新され、社内規定欄に古い記述が残って矛盾する
- **自社で決めたことだけ書く** — 期限・窓口・例外の扱いなど
- 就業規則の該当条文を参照する形が望ましい

## 展開先

- アプリ: ビルド時に型付き辞書へ変換(キーの参照ミス・訳文欠落は CI エラー)
- VitePress: 同じ Markdown をページとして取り込む
- 通知: 文面の一部として参照する(例: 年5日通知の法的注意)
